## 1. 两个版本必须分开看

- **GitHub `main`**：包含情绪日记、自我关怀卡片、沙盘及其本地存档；没有首次进入、安全面板或 AI 服务。远程现已有 `feat/continuous-mood` 分支，但该分支的功能不等于 `main` 已上线。
- **本地工作分支**：在 GitHub `main` 之上增加了本地注册/登录、安全须知、紧急联系人、关键词风险提醒与清除数据入口。这些提交目前不在 GitHub `main`。
- **本地未提交内容**：产品总纲、核心技术方案，以及 `feat/continuous-mood` 上正在改动的情绪记录页面和 `src/mood.js` 正在变化；尚未提交或推送，不计为 GitHub `main` 已实现功能。下文关于旧记录模型与“情绪指数”的判断以 GitHub `main` 为准，不能用来否定正在进行的改造。

## 2. 已实现且建议保留

| 能力 | 代码事实 | 产品处理 |
|---|---|---|
| 情绪日记 | 选择心情、强度、触发标签、自由文字；保存到 `xinxu.entries.v1`；可查看、删除 | 保留作为低门槛表达入口；调整数据结构和记录规则 |
| 回看 | 最近 14 天日历、曲线、标签出现次数和历史记录 | 保留回看能力，修改“指数”“触发原因”等可能过度解释的表达 |
| 简单自助工具 | 呼吸练习、1 分钟伸展、白噪音有实际交互 | 保留为行动候选；由用户选择，避免宣称适合某种心情或必然有效 |
| 沙盘 | 挖/堆沙、沙具摆放、草稿、作品保存与打开、缩略图；可选心情关联日记 | 保留非语言表达入口；暂不自动解读作品 |
| 沙盘见证 | 从预写问题中随机选一句，不自动评价作品 | 保留自由表达原则；如接入 AI，需保证同样的解释边界 |
| 本地数据控制（仅本地分支） | 安全与支持面板可查看/修改联系人、重读须知、清除已列出的数据键 | 保留数据可控思路；新增 AI 数据前重设计删除范围和告知 |

## 3. 不必继续加重，或建议延后

| 当前/候选功能 | 建议 | 原因 |
|---|---|---|
| 将呼吸、运动、白噪音继续扩成大型内容库 | 暂缓扩张 | 目前尚未验证核心 AI 支持是否真的有帮助；内容越多，维护和效果判断越复杂 |
| 沙盘增加更多沙具、画廊、评分或自动象征解释 | 暂缓或取消 | 已有表达能力足以验证价值；自动解释与已定边界冲突 |
| 在浏览器里建立一套“本地账号体系” | 不作为正式身份体系继续扩展 | 当前口令无法保护 `localStorage`，且首次使用增加步骤；跨设备账号须由后端重新设计 |
| 自动量表评分、设备数据、微信账号绑定、多模型/RAG | 首版暂缓 | 用户价值、数据权限、模型质量或平台能力尚未验证 |
| 自动联系紧急联系人 | 不纳入当前计划 | 当前产品没有持续监测和人工接管能力；代码现状也明确不自动发送 |

## 4. 需要大改的部分（按影响排序）

### P0 · 安全提醒不能作为正式风险拦截

本地 `src/safety.js` 只在 `index.html` 保存日记后接收 `entry.note`；它不会检查用户尚未保存的表达、沙盘内容或未来 AI 对话。`promptedToday()` 在风险评估前返回：同一天第一次提醒后，后续明确高风险内容也不会再触发。关键词、强度与连续低落天数规则只适合演示，不能据此承诺识别危机。

**改法**：将风险处理放在每次 AI 输入和输出路径上，独立于主对话提示词；移除对高风险内容的整日静默；定义明确求助、含糊表述、误报和模型不当回复的处理规则，并由专业人员审阅。当前本地提示可作为辅助入口，不作为产品安全保证。

### P0 · 信任说明与未来 AI 数据流冲突

现有页脚和须知写“数据只在浏览器”“没有服务器接收”；这与尚未实现的云端 AI 对话不兼容。须知同时预告未来可能自动联系紧急联系人，容易使用户误解当前能力和未来授权范围。现有“本地登录”只是页面门槛，不能保护本地明文日记、沙盘和联系人。

**改法**：在 AI 上线前按数据类型列明存储位置、模型服务处理方、保留与删除方式；AI 请求单独征求同意；调整与当前能力不符或过早承诺未来自动联络的文案。首次进入流程要检验是否阻碍用户在情绪困扰时快速开始。

### P1 · 记录模型限制了真实情绪变化

GitHub `main` 的 `index.html` 在保存普通日记时会删除当天上一条普通记录，只保留最新一条；沙盘可在当天写入额外记录。日历和趋势又按日期只取一个值。这使“同一天多次波动”“某次行动前后变化”等产品目标难以表达；沙盘保存时写入固定 `intensity: 3`，这个强度不是用户实际输入。本地未提交的情绪模型改造正尝试处理此问题，需完成后再复核。

**改法**：用带时间戳的事件记录，保留一天多条；区分日记、沙盘和后续 AI 会话；趋势按用户选定的聚合方式显示，不替用户覆盖或伪造强度。迁移现有 `v1` 数据时需保留旧记录。

### P1 · 当前“分析”把相关性写成了原因

GitHub `main` 首页按标签统计心情并写“找到影响情绪的原因”，低值标签会触发固定呼吸建议。标签只是用户自行选择，样本量也可能很少；这与“AI 只提出可检验的理解假设、用户掌握解释权”不一致。本地改造完成后需复核文案和推断规则。

**改法**：改成中性回看，例如“这些记录中，提到某标签时你多次记录了较低心情”；展示样本量和记录日期；不要从标签直接推断因果或固定处方呼吸。

### P1 · 自助推荐名义上按心情，实际固定

首页标题写“按心情为你挑选”，但 `renderCare()` 总是渲染同四张卡片，只有第一张文案附加当前心情名称。它尚未根据用户需求选择行动，也没有“不要建议、只想倾听”之类控制。

**改法**：首版先把这些卡片变成用户可主动选择的工具；未来 AI 行动建议依据本次目标和用户偏好，先给少量选项，再由用户决定。

### P1 · 本地存储与数据删除需统一

日记、沙盘、账号与安全数据分别用 `localStorage` 保存。`clearAll()` 使用固定键名清单；后续新增会话、记忆或心情坐标数据时，如果未同步维护清单，“清除全部数据”就可能漏删。沙盘作品含缩略图与高度场，受浏览器存储配额限制；目前没有导出/备份。

**改法**：增加统一的数据键注册与删除边界；明确“本机删除”和“模型服务/未来服务端删除”的不同；设计导出和容量提示。正式云端账号/同步出现时再确定迁移方案。

## 5. 主要未实现能力

| 产品旅程 | 目前缺口 | 首版建议 |
|---|---|---|
| 信任 | GitHub `main` 没有须知；本地分支有本机须知，但没有 AI 数据处理说明 | 按真实 AI 数据流重写简明告知和独立授权 |
| 高效探索 | 现有主要是固定心情、强度、标签和文字；无 AI 澄清、可纠正摘要或多方式切换 | 先做文字自由输入 + 少量可跳过问题 + 用户可纠正摘要 |
| AI 安抚 | 无对话界面、模型调用、阶段编排、策略卡、风格切换 | 单模型 + 最小后端 + 3–4 类受审定支持动作 |
| 连续性 | 无会话历史或用户可管理的长期记忆 | 先做用户确认后保存的偏好与会话摘要、查看/修改/清除 |
| 行动 | 有静态自助工具，无依据本次目标生成的小行动、计划或反馈 | 先做 1–3 个可编辑、可拒绝的行动选项 |
| 效果观察 | 有日记强度与趋势，无一次支持前后自评、帮助/无帮助反馈 | 增加可选的前后主观反馈，不作临床效果宣称 |
| 外部支持 | 本地分支有手动拨号入口；没有可编辑分享草稿或用户确认的外部分享 | 分享先做手动生成、预览和确认；账号绑定延后 |
| AI 技术基础 | 无后端、模型密钥管理、模型供应商评估、AI 输入/输出风险层 | 先解决数据处理协议与可信请求链，再接入 AI |

## 6. 建议的下一轮工作顺序

1. **先修产品表述与安全边界**：明确 GitHub 版和本地版，移除超出实际能力的承诺；修正本地安全提醒的同日静默与输入覆盖范围。
2. **确定 AI 数据流**：选定模型处理方式后，写清发送内容、存储、日志、删除和用户授权；现有本地口令不得复用为云端凭据。
3. **打通最小对话闭环**：文字表达 → 可纠正的理解 → 一种适合的安抚方式 → 用户可选的小行动。
4. **升级记录与回看**：支持时间戳和一天多条记录，删除虚构强度，调整趋势与因果表述。
5. **小范围验证，再扩功能**：观察信任、被理解感、帮助感和失败案例；沙盘 AI 接入、语音、设备数据、社交账号随后决定。
